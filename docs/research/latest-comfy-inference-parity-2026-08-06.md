## Classification and proof rules

- `native-complete`: the stated bounded capability is reached through Dinkster's
  native production runtime and has representative execution proof.
- `partial`: native implementation exists, but supported variants, production
  activation, or representative proof is incomplete.
- `fallback-only`: Dinkster can delegate the capability to its Comfy compatibility
  arm, but the native runtime does not execute it. Workflow success also depends
  on the required nodes translating successfully.
- `absent`: neither a native implementation nor an applicable compatibility
  route was established.
- `intentionally-deferred`: source refuses the capability and ROADMAP names a
  concrete revival trigger.

"Implemented", "tested", "production-wired", "executed", and "live" are
separate facts. Schema exposure, a generic dtype, an importable class, a
synthetic fixture, or a declarative conditioning channel is never counted as
native execution. No currently deployed service was inspected by this audit,
so every `live` cell is `unproven`.

## Explicit platform and claim boundaries

- NVIDIA CUDA and likely CPU are in scope now. AMD/ROCm, Intel XPU, and Apple
  MPS validation are intentionally deferred. Cheaply portable interfaces remain
  required, but those platforms do not block NVIDIA/CPU delivery.
- A native family is never inferred from a layout, detector, dtype, schema,
  fixture, or compatibility route.
- A correctness record is not a performance record. A component timing is not
  end-to-end latency. Internal scheduled overhead is not Dinkster-vs-ComfyUI.
- Live/deployed status remains unproven until a separately authorized service
  observation binds the exact source revision and selected native arm.
